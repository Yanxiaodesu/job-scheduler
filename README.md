# 分布式定时任务调度平台

把散落在各台服务器上的 `crontab` 脚本统一管起来：**可视化配置、到点执行、失败重试、宕机转移、执行留痕**。

一个可以让「调度中心」和「执行器」分别水平扩容的轻量调度平台。核心保证是 **不多不少，恰好执行一次**。

## 为什么做这个

几乎每家公司都有同一个问题：**定时脚本散落在各台机器上，没人知道它跑没跑成功**。

`crontab` 本身能解决「到点执行」，但解决不了：

| 问题 | crontab | 本项目 |
|---|---|---|
| 谁在跑？跑成功了吗？ | 只能翻日志文件 | 每次执行留一条实例记录 + 分步日志 |
| 机器挂了任务怎么办？ | 任务静静消失 | 心跳检测 + 故障转移 |
| 失败了要重试 | 自己写脚本 | 配置 `max_retry` 即可 |
| 服务重启期间错过的任务 | 永远丢了 | misfire 补偿策略 |
| 多台机器同时跑同一个任务 | 重复执行 | 保证恰好一次 |
| 任务改了要登机器 | 是的 | HTTP API 管理 |

## 架构

```
        ┌──────────────────────────────────┐
        │        调度中心 (Admin)           │
        │  SchedulerLoop  每秒扫到点任务     │
        │  FailoverTask   故障转移/超时/misfire │
        │  Router         选一个执行器       │
        └───────┬──────────────────┬───────┘
                │ HTTP 派发         │ HTTP 回调
                ▼                  ▲
     ┌──────────────┐    ┌──────────────┐
     │  执行器 9001  │    │  执行器 9002  │
     │ · 注册 / 心跳 │    │ · 注册 / 心跳 │
     │ · 执行任务    │    │ · 执行任务    │
     └──────┬───────┘    └──────┬───────┘
            └─────────┬─────────┘
                      ▼
        ┌──────────────────────────┐
        │  MySQL                   │
        │   job_info        任务定义 │
        │   executor_registry 注册表 │
        │   job_instance    执行实例 │
        │   job_log         执行日志 │
        └──────────────────────────┘
```

**只有「调度中心 + 执行器 + MySQL」三样东西**，没有 Redis、没有注册中心、没有消息队列。

技术栈：`Java 17` / `Spring Boot 4.1` / `MySQL 8` / `JdbcTemplate` / Maven

## 快速开始

### 前置

- JDK 17+
- MySQL 8

### 1. 建库

```bash
mysql -uroot -p < sql/schema.sql
```

### 2. 改数据库连接

`src/main/resources/application.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/job_scheduler?...
    username: root
    password: root      # ← 改成你的
```

### 3. 打包

```bash
mvnw.cmd package -DskipTests      # Windows
./mvnw package -DskipTests        # Linux / macOS
```

### 4. 启动

```bash
# 调度中心
scripts\run.cmd admin 8080

# 执行器（可以起多个）
scripts\run.cmd executor 9001
scripts\run.cmd executor 9002

# 本机单进程调试（同时干两件事）
scripts\run.cmd both 8080
```

### 5. 建个任务试试

```bash
curl -X POST http://127.0.0.1:8080/api/jobs \
  -H "Content-Type: application/json" \
  -d '{"jobName":"hello","cronExpr":"*/5 * * * * *","handlerType":1,"handlerValue":"printTime"}'
```

`*/5 * * * * *` 是 6 段式 cron（秒 分 时 日 月 周），表示每 5 秒一次。

内置的 4 个示例 handler：

| handler | 作用 | 用来验证什么 |
|---|---|---|
| `printTime` | 打印当前时间 | 正常路径、调度精度 |
| `sleep` | 睡 N 秒（`param` 指定） | 执行超时、宕机转移 |
| `alwaysFail` | 必定抛异常 | 失败重试、重试上限 |
| `busy` | CPU 忙等 N 毫秒 | 并发执行 |

### 6. 看运行情况

```bash
curl http://127.0.0.1:8080/api/metrics       # 运行指标
curl http://127.0.0.1:8080/api/jobs          # 任务列表
curl http://127.0.0.1:8080/api/jobs/1/instances   # 执行历史
```

## 核心设计：恰好执行一次

这是整个项目唯一的核心问题。多个调度中心实例同时在线时，**怎么保证一个任务的一个触发时刻只被执行一次**。

用了**三层防护，没有引入任何分布式锁组件**：

### 第一层：唯一键（主要防线）

```sql
-- job_instance 表上
UNIQUE KEY uk_instance (instance_key)   -- instance_key = "jobId:触发时刻"
```

派发前先 `INSERT` 一条实例。**插入成功 = 这次触发归我；抛 DuplicateKeyException = 别人抢先了**。

数据库的唯一键本身就是一把可靠的分布式锁，而且是原子的。

### 第二层：乐观锁（防止把同一个触发时刻推进两次）

```sql
UPDATE job_info
   SET next_trigger_time = :下次
 WHERE id = :id
   AND next_trigger_time = :旧值     -- ← 关键
```

多个 Admin 手里的「旧值」是同一个时刻。第一个更新成功后，第二个的 `WHERE` 不再成立 → 影响 0 行 → 它就知道自己没抢到。

这就是 CAS（Compare-And-Swap）思想，不加锁、不阻塞。

### 第三层：执行器幂等（挡住网络重发）

执行器用 `instanceId + retryCount` 做去重键，重复派发直接忽略。

### 为什么不用 Redis 分布式锁

这是个**刻意的取舍**：

| | 数据库唯一键 | Redis 锁 |
|---|---|---|
| 额外组件 | 不需要 | 需要 |
| 故障点 | 少一个 | 多一个 |
| 性能 | 一般 | 高 |
| 适合场景 | **秒级调度** | 高频、低延迟 |

调度频率只有每秒几十次，数据库完全扛得住。**少一个组件就少一个故障点**。

代价要能说清楚：并发很高时会出现较多「乐观锁失败」，且强依赖数据库可用性。生产环境该用哪个取决于并发量。

### 一个容易写错的顺序

```
① 先落实例（唯一键抢占）
② 再推进 next_trigger_time（乐观锁）
③ 最后派发
```

## 实测数据

### 1. 零重复执行

3 个 Admin 实例并发抢同一个「每 1 秒触发」的任务，**两种调度模式各测一次**：

| 调度模式 | 时长 | 实例总数 | **重复数** | 抢到 | **抢输** |
|---|---|---|---|---|---|
| 轮询（间隔 1000 ms） | 45 s | 82 | **0** | 82 | 11 |
| **内存队列（默认配置）** | 35 s | 35 | **0** | 35 | **70** |

**「抢输」是这里最关键的数字**：它说明真的发生了并发碰撞，而每次都恰好一个人赢、
另一个人退让。没有这个数字，「0 重复」可能只是碰巧没撞上。

看内存队列那一行：3 个 Admin 的内存队列会在**同一毫秒**集体醒来，
抢输次数是轮询模式的 **6 倍多** —— 并发激烈得多，而「恰好一次」依然成立。
**这条比轮询那行更有说服力。**

> 第一次测试用每 2 秒触发的任务，跑了 33 次触发、`抢输 = 0` —— 三个 Admin 的
> 扫描相位错开了，压根没撞上。**那种结果什么都证明不了**，所以改成每 1 秒重测。

### 2. 调度精度

「实际派发时刻 − 计划触发时刻」，每 1 秒触发一次，各采 45 个样本：

| 调度方式 | P50 | P95 | P99 | DB 查询频率 |
|---|---|---|---|---|
| 轮询，间隔 1000 ms | 561 ms | 983 ms | — | ~1 次/秒 |
| 轮询，间隔 200 ms | 108 ms | 199 ms | 208 ms | ~6.4 次/秒 |
| **内存延迟队列（预取）** | **16 ms** | **22 ms** | **23 ms** | **~1 次/秒** |

**内存队列同时赢了两边：精度比 200ms 轮询快约 7 倍，DB 查询却少 6 倍。**
（最大延迟 26ms、最小 3ms —— 抖动很小。）

原因是它换掉了整个思路：

```
轮询     到点了才去查库 → 平均要等半个扫描间隔
预取     提前把「未来 3 秒到点」的任务装进内存 DelayQueue
         → 到点那一刻直接触发，精度取决于定时器唤醒精度
         → 空闲时工作线程阻塞在 take() 上，CPU 占用为 0
```

实测日志里 `[prefetch]` 触发 39 次、`[polling]` **0 次** —— 内存队列完全接管，
轮询退化成纯兜底。

实测才发现平均要等半个间隔（561ms ≈ 1000/2）。想把精度提上去，
缩短间隔是一条会压垮数据库的死路 —— 所以才换了内存队列。


### 3. 故障转移

派一个睡 60 秒的任务，然后把执行器进程 `kill` 掉：

| 时刻 | 事件 |
|---|---|
| 23:11:03 | 执行器最后一次心跳 |
| 23:11:12 | 进程被杀 |
| 23:11:53 | 任务被转移到另一台执行器 |
| 23:12:53 | 执行成功，结果 `睡了 60 秒` |

**转移耗时约 41 秒**（30 秒离线判定 + 30 秒故障转移扫描，实测落在 41 秒）。任务没有丢，最终成功。

### 4. 失败重试

`maxRetry=2` 的任务，执行 3 次后终结：

| 重试次数 | 状态 | 实例数 |
|---|---|---|
| 2 | 失败 | 7 |
| 1 | 待执行（重试中） | 1 |

去重误判（`duplicateIgnored`）= **0**。

### 5. 执行超时看门狗

睡 90 秒、但 `timeoutSec=10` 的任务，10 + 10（宽限）秒后被判定：

```
状态 = 4 (超时)
结果 = 执行超时：超过 10s 未收到回调
```

### 6. 调度吞吐

300 个任务同时到点，测「投递到全部执行完」的耗时：

| | 串行派发 | **并发派发** |
|---|---|---|
| 总耗时 | 66.3 s | **8~9 s** |
| 吞吐 | 4.5 个/秒 | **34~36 个/秒** |
| 成功数 | 204 / 300 | **300 / 300** |
| 重复 | 0 | **0** |

**约 8 倍提升**。这是这个项目里最明显的一处性能优化，详见下面的[踩坑记录](#7-派发是串行的吞吐被-http-往返卡死)。

### 7. 测试

```
Tests run: 45, Failures: 0, Errors: 0, Skipped: 0
```

| 测试类 | 数量 | 覆盖 |
|---|---|---|
| `JobApiTest` | 15 | HTTP 接口层：cron 校验、重名、启停、404、手动触发不影响排期、指标口径 |
| `FailoverTaskTest` | 13 | misfire 跳过/补跑、超时看门狗、离线判定、故障转移、重派与宽限期 |
| `PrefetchSchedulerTest` | 6 | 内存队列：入队、去重、窗口过滤、到点触发、触发后推进时间 |
| `ExactlyOnceTest` | 5 | 20 线程强制造竞争验证唯一键与乐观锁；cron 解析 |
| `RouterTest` | 5 | 轮询均匀性、随机覆盖、空候选、下标溢出 |
| `JobSchedulerApplicationTests` | 1 | 上下文能起来 |

三处值得说的测试设计：

**① 强制造竞争，而不是等它自然发生**

用「起 3 个 Admin 跑一会儿」验证零重复，**依赖它们恰好撞上**。碰巧没撞上
不等于防护有效（第一次测就跑了 33 次触发、`抢输 = 0`，什么都没证明）。
所以用 20 线程同时抢，每次运行都必然撞上：

- `concurrent_tryCreate_onlyOneWins` —— 断言恰好 1 个赢
- `concurrent_advanceTriggerTime_onlyOneWins` —— 断言恰好 1 个 `rowcount=1`

**② 用真的会应答的假执行器**

故障转移的测试用 JDK 自带的 `HttpServer` 起服务。用死地址的话，
只能测到失败路径 —— 而派发失败时实例会被退回 `PENDING`，
根本测不到「转移/补跑到底有没有发出去」。

**③ 单例的易失状态必须显式清场**

`PrefetchScheduler` 是单例，它的 `DelayQueue` 被所有测试共享。
最初只删表没排空队列，上一个测试遗留的任务被工作线程消费掉并真的触发，
导致两个测试失败（「凭空多出一行实例」「队列数对不上」）。
现在 `@BeforeEach` 会先等队列排空再清表。

## 写这个项目时踩的坑

### 1. 「失败重试」被自己的幂等逻辑静默吃掉

**现象**：重试次数不涨，重试像是没发生。

**原因**：执行器用 `instanceId` 做去重键。但**重试派发的就是同一个 `instanceId`** —— 于是重试请求被当成「重复派发」直接忽略，任务既不执行也不报错，静默卡死。

更阴的是：当时起了 2 个执行器，轮询恰好把重试打到了**另一个**执行器上（它有独立的去重集合），所以表面上一切正常。**单执行器下必然暴露。**

**修复**：去重键改成 `instanceId + retryCount`，每次重试都是一个新键。

### 2. 回调守卫放行了 `PENDING`，导致重试次数被重复累加

**现象**：实例的 `retry_count` 比实际尝试次数多。

**原因**：回调的幂等守卫写成了「状态不是终态就接受」，把 `PENDING`（等待重试）也放进来了。于是一条迟到的回调会对着已经是 `PENDING` 的实例**再跑一次 `markRetry`**，白白把重试次数加了一次。

**修复**：两道守卫 —— 只接受 `RUNNING` 状态；且回调里带的 `retryCount` 必须和库里一致，不一致就判定为迟到回调丢弃。

### 3. 设计了「执行超时」但忘了实现，结果抓到卡死的实例

**现象**：压测时发现一个实例永远停在 `RUNNING`，既不成功也不失败，重试也不发生。

**原因**：回调是网络调用，**一定会丢** —— 执行器中途被杀、网络抖动、中心重启，都会让实例永远停在 `RUNNING`。我在设计文档里写了「执行超时处理」，但代码里压根没写。

**修复**：补上超时看门狗，定时捞出 `start_time` 超过 `timeout_sec + 宽限` 的 `RUNNING` 实例，按重试策略处理。

> 它和「执行器离线转移」覆盖的场景不同：离线转移是**整个执行器没了**（靠心跳发现）；超时看门狗是执行器还活着、但**某个任务卡住或回调丢了**。

### 4. 时间列用了秒精度，精度指标根本测不出来

**现象**：算「实际触发 − 计划触发」，结果不是 0 就是 1000ms。

**原因**：`trigger_time` / `start_time` 用的是 `DATETIME`（秒精度）。**两个整秒相减永远是整秒**，测不出毫秒延迟。

**修复**：所有时间列改成 `DATETIME(3)`，写入用 `NOW(3)`。调度系统记录时间戳本来就应该到毫秒。

### 5. 重试后没人重新派发

`markRetry` 把实例退回 `PENDING` 并清空了 `executor_id`，但故障转移只捞「执行器已离线」的实例 —— **没有任何人会去重派它**。补了一个独立的 5 秒重派循环（`FailoverTask#retryPending`），并且加了 5 秒宽限期来避开「建实例 → 标记已派发」之间的空窗。

### 6. 抢输的一方也必须推进 `next_trigger_time`

见上文[核心设计](#一个容易写错的顺序)。不这么做的话，赢家在推进时间前崩溃会让任务永远空转。

### 7. 派发是串行的，吞吐被 HTTP 往返卡死

**现象**：300 个任务同时到点，花了 **66 秒**（4.5 个/秒），而且只有 204 个成功。

**原因**：派发是 **I/O 密集型**操作 —— 每一步都在等 HTTP 往返。串行做的话，
吞吐上限就是「1 ÷ 单次往返时间」，跟 CPU、跟线程池都无关。

顺带还发现：手动触发的实例当时走的是「建完实例就返回，等 5 秒一次的重派循环去发」，
所以点一下按钮要等最多 5 秒才动。

**修复**：把三处重复的派发逻辑抽成 `InstanceDispatcher`，并提供批量并发派发；
手动触发改成当场派发。

**结果**：66.3 s → **8~9 s**，4.5 → **34~36 个/秒**，成功率 204/300 → **300/300**。

### 8. 派发失败后实例卡在「两边都捞不到」的状态

这个是**测试抓出来的**（修完并发派发后，`misfire_rerun` 挂了）。

**原因**：`markDispatched` 会先把实例标成「执行中 + 已分配执行器」，**然后**才发 HTTP。
如果 HTTP 失败了，实例就卡在一个很尴尬的位置：

| 兜底机制 | 捞它的条件 | 为什么捞不到 |
|---|---|---|
| 重派扫描 | `executor_id IS NULL` | executor_id 已经被填上了 |
| 离线转移 | 执行器心跳超时 | 执行器是好的，只是这次没送达 |
| 超时看门狗 | `start_time` 超时 | **只有它能兜住**，但要等几十秒，还会被误判成「超时」 |

**修复**：派发失败时调 `revertToPending` —— 退回 `PENDING` 并清空 `executor_id`，
重派循环 5 秒内就能重新发出去。

注意它和 `markRetry` 的区别：`revertToPending` **不增加** `retry_count`
（这次压根没送到执行器手上，不算一次执行尝试）；`markRetry` 才计。

### 9. 轮询扫描的精度天花板 —— 缩短间隔是条死路

**现象**：调度精度 P50 561ms（扫描间隔 1000ms）。直觉是「把间隔调小」。

**做了一遍**：间隔降到 200ms，P50 确实降到 108ms —— 但 **DB 查询频率从
1 次/秒涨到 6.4 次/秒**。规律很硬：**平均延迟 ≈ 扫描间隔的一半**，
想再快就得继续缩短，而查询频率是线性上涨的。任务一多，先垮的是数据库。

**这条路走不通。** 换思路：**不在「到点」时才发现任务，而是提前装进内存。**

```
预取线程   每 1 秒查一次「未来 3 秒内到点的任务」→ 放进 DelayQueue
工作线程   queue.take() 阻塞等待 → 到点自动醒来 → 触发
```

**结果**：

| | 轮询 200ms | 内存队列 |
|---|---|---|
| P50 | 108 ms | **20 ms** |
| DB 查询 | 6.4 次/秒 | **1 次/秒** |

**精度快 5 倍，DB 压力反而小 6 倍。**

两个实现细节值得一提：

- **用 `DelayQueue.take()` 而不是「每 10ms 看一眼队首」**。后者本质上还是轮询，
  只是不查库 —— 白白占着 CPU。`take()` 在没有任务时是真的挂起。
- **两条路同时开着，不需要协调**。抢占统一走 `JobTrigger.fire`，
  唯一键 + 乐观锁保证谁先抢到算谁的。所以轮询可以留着当兜底，
  防「内存队列漏了 / 进程重启丢了状态」。实测 `[prefetch]` 触发 39 次、
  `[polling]` 0 次 —— 完全接管，但兜底还在。

### 10. 「本机全绿、CI 全红」—— 时钟源不统一

这个项目的 CI 前后红了 **11 次**才跑通。回头看，值得记的不是「修了什么」，
而是**它们全是同一类问题：只在一台机器上验证过**。

| 问题 | 为什么本机看不出来 |
|---|---|
| `mvnw` 没有可执行位 | Windows 没有「可执行位」这个概念 |
| 本机 Maven 配置被提交进仓库（`-s D:\java\m2\settings.xml`） | 那个路径在本机真实存在 |
| `DATETIME` 列混用 `Timestamp` / `LocalDateTime` | 本机 JVM 时区和 JDBC URL 里的 `serverTimezone` 恰好都是 `+08:00`，驱动的时区转换**退化成恒等变换** |
| 预取的到期时刻用 JVM 时区解释数据库时间 | 同上，两边时区一致时算出来刚好是对的 |
| 算「下一次触发时刻」用了 `LocalDateTime.now()` | 同上 |

**后三个是真正的生产 bug，不是测试问题。** 尤其是最后一个：`next_trigger_time`
是数据库的时钟写进去的，调度循环又拿它和数据库的 `NOW()` 比；中间却用 JVM 的时钟
算「下一次」。两边不一致时算出来的时刻可能**落在过去** —— 任务会被反复触发，
恰恰是「恰好一次」要防的事。

统一后的原则很简单：

> **时间相关的计算，时钟源只能有一个，而且必须是数据库。**
> JVM 只负责相对量（差多少微秒、延迟多久唤醒）。

具体落地：
- 时间列读写用 `getObject(col, LocalDateTime.class)` / `setObject`，不经过 `Timestamp`
- 预取的到期时长由 `TIMESTAMPDIFF(MICROSECOND, NOW(3), next_trigger_time)` 算
- 算下次触发时刻用 `SELECT NOW(3)`（`JobInfoRepo.now()`）
- **测试也不再依赖真实时钟**：把「处理一个到点任务」抽成 `process()`，
  工作线程和测试共用；测试直接调 `fireDueNow()` 同步触发，
  不再 `sleep` 等工作线程自己醒

最后一条顺带把 `PrefetchSchedulerTest` 从 **86 秒降到 1 秒**，而且不再 flaky。

> 验证方式也值得说一句：光跑一遍不算数。先造出「两边时区不一致」的环境
> （本机 MySQL 是 `+08:00`，强制 JVM 用 UTC —— 这时旧代码必挂），
> 改完再在 **UTC/UTC、UTC/+08:00、+08:00/+08:00 三种组合**下各跑一遍。

## 已知的取舍与局限

| 局限 | 说明 | 要改怎么做 |
|---|---|---|
| **Admin 是单点** | 现在 3 个 Admin 同时跑没问题（靠唯一键+乐观锁），但没有 leader 选举，也没做 Admin 的高可用接入 | 抢锁选举 leader，只让 leader 扫描 |
| **调度精度可再提升** | 内存队列已做到 P50 17ms，但仍是单一 DelayQueue，多核下没并行 | 分片成多个队列，各自一个工作线程（Netty `HashedWheelTimer` 的分片思路） |
| **执行器去重是内存集合** | 进程重启就失效 | 落库唯一键或 Redis（带 TTL） |
| **超时不会真正中断任务** | 看门狗只把实例标记为超时，执行器线程还在跑（Java 中断 `Thread.sleep` 需要额外处理） | 执行器侧用 `Future.cancel(true)` + 捕获中断 |
| **没有分片** | 一个大任务不能拆到多台机器并行 | 加分片广播路由 |
| **没有告警** | 失败只有记录，不会通知人 | 接 Webhook / 钉钉 |
| **任务参数只有单个字符串** | 复杂参数得自己序列化 | 改成 JSON 字段 |
| **执行日志量大** | 每个任务实例都会写日志，没有清理策略 | 加定期归档/清理 |
