# 分布式定时任务调度平台

把散落在各台服务器上的 `crontab` 脚本统一管起来：**可视化配置、到点执行、失败重试、宕机转移、执行留痕**。

一个可以让「调度中心」和「执行器」分别水平扩容的轻量调度平台。核心保证是 **不多不少，恰好执行一次**。

## 为什么做这个

几乎每家公司都有同一个问题：**定时脚本散落在各台机器上，没人知道它跑没跑成功**。

`crontab` 本身能解决「到点执行」，但解决不了：

| 问题 | crontab | 本项目 |
|---|---|---|
| 谁在跑？跑成功了吗？ | 只能翻日志文件 | 每次执行留一条实例记录 + 分步日志 |
| 机器挂了任务怎么办？ | 任务静静消失 | 心跳检测 + 故障转移 |
| 失败了要重试 | 自己写脚本 | 配置 `max_retry` 即可 |
| 服务重启期间错过的任务 | 永远丢了 | misfire 补偿策略 |
| 多台机器同时跑同一个任务 | 重复执行 | 保证恰好一次 |
| 任务改了要登机器 | 是的 | HTTP API 管理 |

## 架构

```
        ┌──────────────────────────────────┐
        │        调度中心 (Admin)           │
        │  SchedulerLoop  每秒扫到点任务     │
        │  FailoverTask   故障转移/超时/misfire │
        │  Router         选一个执行器       │
        └───────┬──────────────────┬───────┘
                │ HTTP 派发         │ HTTP 回调
                ▼                  ▲
     ┌──────────────┐    ┌──────────────┐
     │  执行器 9001  │    │  执行器 9002  │
     │ · 注册 / 心跳 │    │ · 注册 / 心跳 │
     │ · 执行任务    │    │ · 执行任务    │
     └──────┬───────┘    └──────┬───────┘
            └─────────┬─────────┘
                      ▼
        ┌──────────────────────────┐
        │  MySQL                   │
        │   job_info        任务定义 │
        │   executor_registry 注册表 │
        │   job_instance    执行实例 │
        │   job_log         执行日志 │
        └──────────────────────────┘
```

**只有「调度中心 + 执行器 + MySQL」三样东西**，没有 Redis、没有注册中心、没有消息队列。

技术栈：`Java 17` / `Spring Boot 4.1` / `MySQL 8` / `JdbcTemplate` / Maven

## 快速开始

### 前置

- JDK 17+
- MySQL 8

### 1. 建库

```bash
mysql -uroot -p < sql/schema.sql
```

### 2. 改数据库连接

`src/main/resources/application.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/job_scheduler?...
    username: root
    password: root      # ← 改成你的
```

### 3. 打包

```bash
mvnw.cmd package -DskipTests      # Windows
./mvnw package -DskipTests        # Linux / macOS
```

### 4. 启动

```bash
# 调度中心
scripts\run.cmd admin 8080

# 执行器（可以起多个）
scripts\run.cmd executor 9001
scripts\run.cmd executor 9002

# 本机单进程调试（同时干两件事）
scripts\run.cmd both 8080
```

### 5. 建个任务试试

```bash
curl -X POST http://127.0.0.1:8080/api/jobs \
  -H "Content-Type: application/json" \
  -d '{"jobName":"hello","cronExpr":"*/5 * * * * *","handlerType":1,"handlerValue":"printTime"}'
```

`*/5 * * * * *` 是 6 段式 cron（秒 分 时 日 月 周），表示每 5 秒一次。

内置的 4 个示例 handler：

| handler | 作用 | 用来验证什么 |
|---|---|---|
| `printTime` | 打印当前时间 | 正常路径、调度精度 |
| `sleep` | 睡 N 秒（`param` 指定） | 执行超时、宕机转移 |
| `alwaysFail` | 必定抛异常 | 失败重试、重试上限 |
| `busy` | CPU 忙等 N 毫秒 | 并发执行 |

### 6. 看运行情况

```bash
curl http://127.0.0.1:8080/api/metrics       # 运行指标
curl http://127.0.0.1:8080/api/jobs          # 任务列表
curl http://127.0.0.1:8080/api/jobs/1/instances   # 执行历史
```

## 核心设计：恰好执行一次

这是整个项目唯一的核心问题。多个调度中心实例同时在线时，**怎么保证一个任务的一个触发时刻只被执行一次**。

用了**三层防护，没有引入任何分布式锁组件**：

### 第一层：唯一键（主要防线）

```sql
-- job_instance 表上
UNIQUE KEY uk_instance (instance_key)   -- instance_key = "jobId:触发时刻"
```

派发前先 `INSERT` 一条实例。**插入成功 = 这次触发归我；抛 DuplicateKeyException = 别人抢先了**。

数据库的唯一键本身就是一把可靠的分布式锁，而且是原子的。

### 第二层：乐观锁（防止把同一个触发时刻推进两次）

```sql
UPDATE job_info
   SET next_trigger_time = :下次
 WHERE id = :id
   AND next_trigger_time = :旧值     -- ← 关键
```

多个 Admin 手里的「旧值」是同一个时刻。第一个更新成功后，第二个的 `WHERE` 不再成立 → 影响 0 行 → 它就知道自己没抢到。

这就是 CAS（Compare-And-Swap）思想，不加锁、不阻塞。

### 第三层：执行器幂等（挡住网络重发）

执行器用 `instanceId + retryCount` 做去重键，重复派发直接忽略。

### 为什么不用 Redis 分布式锁

这是个**刻意的取舍**：

| | 数据库唯一键 | Redis 锁 |
|---|---|---|
| 额外组件 | 不需要 | 需要 |
| 故障点 | 少一个 | 多一个 |
| 性能 | 一般 | 高 |
| 适合场景 | **秒级调度** | 高频、低延迟 |

调度频率只有每秒几十次，数据库完全扛得住。**少一个组件就少一个故障点**。

代价要能说清楚：并发很高时会出现较多「乐观锁失败」，且强依赖数据库可用性。生产环境该用哪个取决于并发量。

### 一个容易写错的顺序

```
① 先落实例（唯一键抢占）
② 再推进 next_trigger_time（乐观锁）
③ 最后派发
```

为什么不能反过来？假设反过来（先推进时间、再落实例），如果推进成功后进程崩了，`next_trigger_time` 已经变了、但实例没落下来 —— **这次触发就永远丢了**，而且没有任何人会知道。

还有一处更隐蔽：**抢输的一方也要执行一次「推进时间」**。

场景：赢家落实例成功、但在推进时间之前崩了。此时 `next_trigger_time` 还停在旧值，下一轮又会被扫到。如果抢输的一方只做「跳过」，任务就会**永远卡在这一刻反复空转**。让失败方也执行一次带条件的推进，就自然收敛了。

## 实测数据

以下都是本机真实跑出来的，不是估计值。

### 1. 零重复执行

3 个 Admin 实例同时扫同一个每 1 秒触发的任务，跑 45 秒：

| 指标 | 数值 |
|---|---|
| 实例总数 | 82 |
| 不同触发时刻 | 82 |
| **重复数** | **0** |
| 抢到 | 82 |
| **抢输** | **11** |

**`抢输 = 11` 是这里最关键的数字**：它说明真的发生了 11 次并发碰撞，而每次都恰好一个人赢、另一个人退让。没有这个数字，「0 重复」可能只是碰巧没撞上。

> 第一次测试用每 2 秒触发的任务，跑了 33 次触发、`抢输 = 0` —— 三个 Admin 的扫描相位错开了，压根没撞上。**那种结果什么都证明不了**，所以改成每 1 秒重测。

### 2. 调度精度

「实际派发时刻 − 计划触发时刻」，每 1 秒触发一次，采 90 个样本：

| 扫描间隔 | P50 | P95 | 最大 | DB 查询频率 |
|---|---|---|---|---|
| 1000 ms | 561 ms | 983 ms | 1366 ms | ~1 次/秒 |
| **200 ms** | **108 ms** | **199 ms** | **217 ms** | ~6.4 次/秒 |

**精度提升 5.2 倍，代价是 DB 查询多 6.4 倍。**

规律很明确：**轮询式扫描的平均延迟 ≈ 扫描间隔的一半**（544ms ≈ 1000/2，验证吻合）。

这个数字一开始把我打脸了 —— 我原本以为「1 秒扫一次 = 秒级精度」，实测才发现平均要等半个间隔。

### 3. 故障转移

派一个睡 60 秒的任务，然后把执行器进程 `kill` 掉：

| 时刻 | 事件 |
|---|---|
| 23:11:03 | 执行器最后一次心跳 |
| 23:11:12 | 进程被杀 |
| 23:11:53 | 任务被转移到另一台执行器 |
| 23:12:53 | 执行成功，结果 `睡了 60 秒` |

**转移耗时约 41 秒**（30 秒离线判定 + 30 秒故障转移扫描，实测落在 41 秒）。任务没有丢，最终成功。

### 4. 失败重试

`maxRetry=2` 的任务，执行 3 次后终结：

| 重试次数 | 状态 | 实例数 |
|---|---|---|
| 2 | 失败 | 7 |
| 1 | 待执行（重试中） | 1 |

去重误判（`duplicateIgnored`）= **0**。

### 5. 执行超时看门狗

睡 90 秒、但 `timeoutSec=10` 的任务，10 + 10（宽限）秒后被判定：

```
状态 = 4 (超时)
结果 = 执行超时：超过 10s 未收到回调
```

### 6. 调度吞吐

300 个任务同时到点，测「投递到全部执行完」的耗时：

| | 串行派发 | **并发派发** |
|---|---|---|
| 总耗时 | 66.3 s | **8.8 s** |
| 吞吐 | 4.5 个/秒 | **34.0 个/秒** |
| 成功数 | 204 / 300 | **300 / 300** |
| 重复 | 0 | **0** |

**7.5 倍提升**。这是这个项目里最明显的一处性能优化，详见下面的[踩坑记录](#7-派发是串行的吞吐被-http-往返卡死)。

### 7. 测试

```
Tests run: 24, Failures: 0, Errors: 0, Skipped: 0
```

| 测试类 | 数量 | 覆盖 |
|---|---|---|
| `ExactlyOnceTest` | 5 | 20 线程强制造竞争，验证唯一键/乐观锁只放一个人过；cron 解析 |
| `FailoverTaskTest` | 13 | misfire 跳过/补跑、超时看门狗、离线判定、故障转移、重派 |
| `RouterTest` | 5 | 轮询均匀性、随机覆盖、空候选、下标溢出 |
| `JobSchedulerApplicationTests` | 1 | 上下文能起来 |

其中两个是**强制造竞争**的确定性测试（20 线程同时抢占）：

- `concurrent_tryCreate_onlyOneWins` —— 20 线程抢同一个 `instance_key`，断言恰好 1 个赢
- `concurrent_advanceTriggerTime_onlyOneWins` —— 20 线程抢推进同一个旧值，断言恰好 1 个 `rowcount=1`

为什么要有这两个：用「起 3 个 Admin 跑一会儿」的方式验证，**依赖它们恰好撞上**。碰巧没撞上不等于防护有效。多线程测试让每次运行都必然撞上。

故障转移相关的测试用 JDK 自带的 `HttpServer` 起了**真的会应答的假执行器** —— 因为派发失败时实例会被退回 `PENDING`，如果地址是死的，就只能测到失败路径，测不到「转移/补跑到底有没有发出去」。

### 8. 一键复现

上面所有数字都可以自己跑一遍：

```bash
# 先起集群（3 个 Admin + 2 个执行器）
scripts\run.cmd admin    8080
scripts\run.cmd admin    8081
scripts\run.cmd admin    8082
scripts\run.cmd executor 9001
scripts\run.cmd executor 9002

# 然后
python scripts/benchmark.py
```

脚本会依次跑「零重复 → 调度精度 → 调度吞吐」三项并输出汇总。
只用 Python 标准库，不需要装任何依赖。

## 和 xxl-job 的差异

参考项目：[xxl-job](https://github.com/xuxueli/xxl-job)（30.6k stars）是最主流的国产调度平台。但它的体量（39 MB 代码、上千个类）不适合作为学习项目。

**主动砍掉的部分**（都是刻意的）：

| xxl-job 有 | 本项目 | 为什么砍 |
|---|---|---|
| Netty 内嵌 HTTP + 自研 RPC | 普通 HTTP 调用 | 通信不是这个项目的重点，造 RPC 是本末倒置 |
| GLUE 在线编辑脚本 | 内置 handler + HTTP 回调 | 动态编译是另一个量级的复杂度 |
| 分片广播 / MapReduce | 单机路由 | 高级话题，讲不清楚不如不做 |
| 10 种路由策略 | 轮询 + 随机 | **「为什么需要路由」才是考点**，不是策略数量 |
| 完整 Vue 管理后台 | 纯 API | 前端不是后端项目要证明的东西 |
| 告警（邮件/钉钉/Webhook） | 失败留痕 + 指标 | 可选加分项 |
| 多语言执行器 | 只做 Java | 同上 |
| Redis / 注册中心 | 只用 MySQL | 少一个组件少一个故障点 |

**砍完剩下的**：任务定义 → 到点触发 → 选执行器 → 执行 → 上报 → 失败重试 → 宕机转移。这一条链路就是全部。

## 写这个项目时踩的坑

这一节可能是全文最有价值的部分。

### 1. 「失败重试」被自己的幂等逻辑静默吃掉

**现象**：重试次数不涨，重试像是没发生。

**原因**：执行器用 `instanceId` 做去重键。但**重试派发的就是同一个 `instanceId`** —— 于是重试请求被当成「重复派发」直接忽略，任务既不执行也不报错，静默卡死。

更阴的是：当时起了 2 个执行器，轮询恰好把重试打到了**另一个**执行器上（它有独立的去重集合），所以表面上一切正常。**单执行器下必然暴露。**

**修复**：去重键改成 `instanceId + retryCount`，每次重试都是一个新键。

### 2. 回调守卫放行了 `PENDING`，导致重试次数被重复累加

**现象**：实例的 `retry_count` 比实际尝试次数多。

**原因**：回调的幂等守卫写成了「状态不是终态就接受」，把 `PENDING`（等待重试）也放进来了。于是一条迟到的回调会对着已经是 `PENDING` 的实例**再跑一次 `markRetry`**，白白把重试次数加了一次。

**修复**：两道守卫 —— 只接受 `RUNNING` 状态；且回调里带的 `retryCount` 必须和库里一致，不一致就判定为迟到回调丢弃。

### 3. 设计了「执行超时」但忘了实现，结果抓到卡死的实例

**现象**：压测时发现一个实例永远停在 `RUNNING`，既不成功也不失败，重试也不发生。

**原因**：回调是网络调用，**一定会丢** —— 执行器中途被杀、网络抖动、中心重启，都会让实例永远停在 `RUNNING`。我在设计文档里写了「执行超时处理」，但代码里压根没写。

**修复**：补上超时看门狗，定时捞出 `start_time` 超过 `timeout_sec + 宽限` 的 `RUNNING` 实例，按重试策略处理。

> 它和「执行器离线转移」覆盖的场景不同：离线转移是**整个执行器没了**（靠心跳发现）；超时看门狗是执行器还活着、但**某个任务卡住或回调丢了**。

### 4. 时间列用了秒精度，精度指标根本测不出来

**现象**：算「实际触发 − 计划触发」，结果不是 0 就是 1000ms。

**原因**：`trigger_time` / `start_time` 用的是 `DATETIME`（秒精度）。**两个整秒相减永远是整秒**，测不出毫秒延迟。

**修复**：所有时间列改成 `DATETIME(3)`，写入用 `NOW(3)`。调度系统记录时间戳本来就应该到毫秒。

### 5. 重试后没人重新派发

`markRetry` 把实例退回 `PENDING` 并清空了 `executor_id`，但故障转移只捞「执行器已离线」的实例 —— **没有任何人会去重派它**。补了一个独立的 5 秒重派循环（`FailoverTask#retryPending`），并且加了 5 秒宽限期来避开「建实例 → 标记已派发」之间的空窗。

### 6. 抢输的一方也必须推进 `next_trigger_time`

见上文[核心设计](#一个容易写错的顺序)。不这么做的话，赢家在推进时间前崩溃会让任务永远空转。

### 7. 派发是串行的，吞吐被 HTTP 往返卡死

**现象**：300 个任务同时到点，花了 **66 秒**（4.5 个/秒），而且只有 204 个成功。

**原因**：派发是 **I/O 密集型**操作 —— 每一步都在等 HTTP 往返。串行做的话，
吞吐上限就是「1 ÷ 单次往返时间」，跟 CPU、跟线程池都无关。

顺带还发现：手动触发的实例当时走的是「建完实例就返回，等 5 秒一次的重派循环去发」，
所以点一下按钮要等最多 5 秒才动。

**修复**：把三处重复的派发逻辑抽成 `InstanceDispatcher`，并提供批量并发派发；
手动触发改成当场派发。

**结果**：66.3 s → **8.8 s**，4.5 → **34 个/秒**，成功率 204/300 → **300/300**。

### 8. 派发失败后实例卡在「两边都捞不到」的状态

这个是**测试抓出来的**（修完并发派发后，`misfire_rerun` 挂了）。

**原因**：`markDispatched` 会先把实例标成「执行中 + 已分配执行器」，**然后**才发 HTTP。
如果 HTTP 失败了，实例就卡在一个很尴尬的位置：

| 兜底机制 | 捞它的条件 | 为什么捞不到 |
|---|---|---|
| 重派扫描 | `executor_id IS NULL` | executor_id 已经被填上了 |
| 离线转移 | 执行器心跳超时 | 执行器是好的，只是这次没送达 |
| 超时看门狗 | `start_time` 超时 | **只有它能兜住**，但要等几十秒，还会被误判成「超时」 |

**修复**：派发失败时调 `revertToPending` —— 退回 `PENDING` 并清空 `executor_id`，
重派循环 5 秒内就能重新发出去。

注意它和 `markRetry` 的区别：`revertToPending` **不增加** `retry_count`
（这次压根没送到执行器手上，不算一次执行尝试）；`markRetry` 才计。

## 已知的取舍与局限

**这些不是「没想到」，是蒸馏版的自觉选择。** 面试被问到时如实说，比硬撑强。

| 局限 | 说明 | 要改怎么做 |
|---|---|---|
| **Admin 是单点** | 现在 3 个 Admin 同时跑没问题（靠唯一键+乐观锁），但没有 leader 选举，也没做 Admin 的高可用接入 | 抢锁选举 leader，只让 leader 扫描 |
| **扫描是轮询** | 每秒查一次库，任务多了 DB 压力线性上升 | 换**时间轮**（参考 Netty `HashedWheelTimer`），只把即将到点的任务加载进内存堆 |
| **执行器去重是内存集合** | 进程重启就失效 | 落库唯一键或 Redis（带 TTL） |
| **超时不会真正中断任务** | 看门狗只把实例标记为超时，执行器线程还在跑（Java 中断 `Thread.sleep` 需要额外处理） | 执行器侧用 `Future.cancel(true)` + 捕获中断 |
| **没有分片** | 一个大任务不能拆到多台机器并行 | 加分片广播路由 |
| **没有告警** | 失败只有记录，不会通知人 | 接 Webhook / 钉钉 |
| **任务参数只有单个字符串** | 复杂参数得自己序列化 | 改成 JSON 字段 |
| **执行日志量大** | 每个任务实例都会写日志，没有清理策略 | 加定期归档/清理 |

## 表结构

4 张表，见 [`sql/schema.sql`](sql/schema.sql)。

| 表 | 作用 | 关键设计 |
|---|---|---|
| `job_info` | 任务定义 | `next_trigger_time` 是调度循环唯一扫描依据，建了 `(status, next_trigger_time)` 索引 |
| `executor_registry` | 执行器注册表 | `last_heartbeat` 是判断死活的唯一依据；用 UPSERT 一条 SQL 完成注册/续约 |
| `job_instance` | 每次触发一条 | **`UNIQUE KEY (instance_key)` 是「恰好一次」的主要防线** |
| `job_log` | 执行日志 | 回答「这个任务为什么失败」 |

## 面试可能被问到的

### Q：怎么保证任务不重复执行？

三层防护，**没有用 Redis 锁**：

1. `job_instance` 的唯一键 `(instance_key)`，`instance_key = "jobId:触发时刻"` —— 落不进去说明别人抢先了
2. `UPDATE job_info SET next_trigger_time=? WHERE id=? AND next_trigger_time=?` —— 乐观锁，旧值对不上就影响 0 行
3. 执行器用 `instanceId + retryCount` 幂等，挡住网络重发

实测：3 个 Admin 并发，82 个实例、0 重复、11 次真实碰撞。

### Q：为什么不用 Redis 分布式锁？

调度频率是秒级（每秒几十次），数据库完全够用。**少一个组件就少一个故障点**。

代价：并发很高时乐观锁失败率上升，且强依赖数据库可用性。生产环境看并发量决定。

### Q：调度精度怎么保证？

轮询式扫描的**平均延迟 ≈ 扫描间隔的一半**。实测：

- 1000ms 间隔 → P50 **561ms**
- 200ms 间隔 → P50 **108ms**

想再快就得换**时间轮**：把即将到点的任务预先加载进内存的最小堆，到点直接从内存触发，不查库。

### Q：执行器挂了任务不就丢了？

三层兜底，覆盖不同场景：

1. **心跳超时** → 标记离线 → 转移它身上没跑完的实例（实测 41 秒）
2. **派发时恰好挂了** → 实例留在 `PENDING`，被重派循环捡走
3. **回调丢了/任务卡死** → 超时看门狗捞出来，按重试策略处理

所有查询只挑 `PENDING` / `RUNNING`，**绝不重跑已成功或已失败的任务**。

### Q：调度中心自己挂了怎么办？

现在是单点（**如实承认**）。3 个 Admin 同时跑不会重复派发，但没做 leader 选举。

要改的话：抢锁选 leader，只有 leader 扫描；或者把 `next_trigger_time` 的抢占做得更激进，让所有 Admin 都能安全地竞争。

### Q：为什么不先推进时间再落实例？

那样的话，推进成功后进程崩溃，`next_trigger_time` 变了但实例没落下来 —— **这次触发永远丢失**，而且没人会发现。

先落实例的话，崩溃后实例还在 `PENDING`，故障转移会捡走它。

### Q：为什么用 JdbcTemplate 不用 MyBatis？

这个项目的核心是几条自己写的 SQL（扫到点任务、乐观锁抢占、心跳超时判定）。用 JdbcTemplate 每条 SQL 都看得见、讲得清，也少一层抽象。**CRUD 型项目才需要 ORM 来省事。**

### Q：数据库压力多大？

扫描间隔 200ms 时约 **6.4 次/秒** 的查询。任务量再大就该上时间轮了。
